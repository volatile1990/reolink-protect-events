# Heimserver releases

The [installed host layout and bootstrap requirements](../deploy/heimserver/README.md)
record the server/UDM addresses, all five own services, the macvlan host shim,
SSH forwarding and socket permissions, private file paths and local hook setup.

The dedicated server runs Events, the media monitor, Controls and the archive
proxy from one public release below `/srv/cameras/protect/releases/<digest>`.
`current` is an absolute symlink to that release. The fixed systemd units use
`current/events`, `current/controls/worker.py` and `current/archive/proxy.cjs`.
Python units must set `PYTHONDONTWRITEBYTECODE=1`: a release is verified against
its exact file list, including on later checks.

Private configuration stays in `config/events.json` and `config/controls.json`;
the journal and monitor/recovery data stay in `state/events` and `state/monitor`.
The release tool never replaces or restores those files, installs dependencies,
edits units, or restarts Protect, Docker, cameras or the SSH tunnel.

Use the pinned local SSH alias `heimserver`; it must support noninteractive
`sudo -n`. The tool sends its public deployment code and request through stdin.
It never downloads private configuration or raw remote stderr.

```powershell
python tools/protect_server.py status
python tools/protect_server.py check
python tools/protect_server.py stage --bundle reviewed-public-release.zip --digest <new-digest>
python tools/protect_server.py check --digest <new-digest>
python tools/protect_server.py activate --digest <new-digest> --expected-current <current-digest>
python tools/protect_server.py rollback --expected-current <current-digest>
```

The ZIP contains only `release.json`, Python source below
`events/reolink_protect_events/`, `controls/worker.py`, `archive/proxy.cjs` and
`archive/aac-clock.cjs`. The root manifest has `schemaVersion: 1`, `version: 2.0.0`, `digest`, and
`members`, each with `path`, `sha256`, and `bytes`. The digest is SHA256 of
`json.dumps(members, sort_keys=True, separators=(',', ':')).encode()`; the
manifest itself is excluded from members. No private configuration, vendored
dependencies, symlinks, additional files or generated bytecode are accepted.
Python is syntax-checked without execution; Node checks both archive sources.

`check` requires `protectRemote` and the `udm-protect` SSH alias. It verifies the
audited Protect version, database schema and exact six-camera mapping through
the remote connector; there is no local Protect fallback. It also reports the
installed Pillow version. Activation compares the expected current digest,
switches all four components together and checks fresh Events health plus the
own active units. A full media-monitor rotation and real archive/live playback
remain separate acceptance checks; the result explicitly reports
`mediaCycleVerified: false`.

Rollback selects only the recorded immediate previous release. It keeps current
private state, so it is not a database rollback. On an activation failure, the
tool only takes back its own current-link/metadata bytes; a foreign edit is
left for inspection. `manualInspectionRequired` means an automatic return or
private-configuration preservation could not be established.

After migration, the legacy UDM installer permits status reads and rejects its
mutations with `migrated_to_heimserver` when the server-architecture marker or a
`protectRemote` configuration is present. New code releases use this server
tool rather than the retired UDM install path.

## Bridge controller

The private controller used by `tools/protect_ops.py` explicitly selects the
new architecture with these public settings in addition to its existing local
repository, protected bridge connector and receipt-directory paths:

```json
{
  "architecture": "heimserver",
  "protectSshAlias": "unifi-dream-machine",
  "serverSshAlias": "heimserver",
  "bridgeSettings": {
    "scope": "/srv/cameras/bridges",
    "runtimeUid": 1026,
    "renderGroup": 992,
    "restartPolicy": "unless-stopped",
    "maintenanceMode": "deployment-lock"
  }
}
```

The protected bridge connector must also target the Heimserver. Selecting an
architecture does not rewrite that private connector or configuration.

This profile is a **bridge-only** update: isolated build/hardware audit, six
sequential camera changes, actual live/recording AV gates and scoped rollback
stay in place. Health, recovery, journal evidence and the monitor's owned
maintenance marker use the server's fixed config/state paths. Real recording
discovery and export reads also run on the server, using its existing loopback
snapshot tunnel at port 17080; media decoding remains in desktop RAM.

The native Protect compatibility check stays on the UDM, where Protect, its
database and owned UI metadata remain. Once the server-architecture marker is
present, it reads only `/data/reolink-protect-connector/compatibility.json` with
`protectUserId` and six `bridges` entries containing `cameraId`, `host` and
optional pinned `mac`. No real or placeholder bridge credentials are needed.
The live owned UI/Automatic receipts and their referenced backup manifests
remain integration evidence on the UDM. Their original settings-baseline hash
is preserved and its current match is reported. Compatibility checks the
audited current source/profile/routing contract instead of freezing unrelated
user settings to an old installation date. Exact service/AAC/UI/guard bytes and
ownership remain mandatory. The controller separately binds a complete current
settings hash before/after each update, so changes during that transaction
still prevent a successful commit.

The installed four-component server-code digest must remain identical for the
whole bridge transaction. The bridge controller never installs an old Events
ZIP or changes that server release. Events/Controls/archive code uses the
separate server release command. A finished bridge receipt may coexist with a
later independently verified server-code update; a running transaction remains
pinned to its original server digest. Old UDM receipts cannot be resumed under
the new architecture.
